# Why I'm switching back to a static site generator

I used React for years. Svelte, Next.js—you name it.

Now? Back with Hugo (or Hugo-based workflows). Static HTML delivered directly from disk in milliseconds rather than server-rendered latency and database complexity overhead that didn't need existing here at all.


## What I was trying to solve then vs now

Initially the React/Serverside setup solved problems we never had:
- Search indexing: GSC, Algolia handled this already
- Comment systems: Decoupled services like Disqus/utterances/giscus could live anywhere 
- Dynamic data needed a DB? Not for my use case. Content doesn't change fast enough to warrant that.
- Analytics + personal stats dashboarding were easier on the server side anyway

We weren't building an app with user sessions, permissions or real-time collaboration—we're just publishing thoughts in markdown and serving them out.

All of this became unnecessary overhead.


## What I'm gaining back now (and why it matters)

**Speed.**
- Disk to browser is orders faster than API call → template compile → render
- Freshness: Every page loads exactly what's on disk, no cache invalidation issues

Simplicity.
No build step in production means:
 - No hot-reload race conditions or server restarts during deployment 
  fewer moving parts = easier backups and rollbacks (just rsync files)
Deployment is literally just `rsync . s3:` instead of container orchestration with health checks, timeouts etc.

Trust & transparency.  
The source repository IS the deployable artifact—no mystery about what actually got deployed vs tested locally because it's identical at all steps.


## Where static makes sense (and where I'd still consider React)

**Good fits for Hugo/Svelte/astro:**
- Documentation sites with clear content hierarchy
 - Blogs and newsletters, especially opinionated workflows or "how-to" guides  
  Portfolios/showcases of existing work

| Tradeoff | Static Site Gen like Astro/Hugo/Gatsby |
|--|
Pros—performance (ms-level), simplicity (<10 files total for most blogs no build complexity; zero dependencies in prod)
- transparency & trust, reproducible builds
Cons — less interactivity without JS overhead or external services.

**Where React/Next.js still wins:**
 - Dashboards with real-time data feeds that update continuously during sessions (server events streaming).
  Social apps where you need persistent user states and collaborative experiences per request.
   Complex multi-step wizards requiring server-side validation/stateful flows at scale.


## The lesson learned

Most things we "solved" by moving to React were problems in search engine behavior or external service architecture, not fundamental constraints of what blogging should be.

Simplicity is often better than flexibility when you're just publishing thoughts. Complexity pays off only once the use case demands it—dynamic features and collaboration patterns that justify a runtime environment with statefulness.


## Where I'm going next

I'll still keep React skills in my toolbox for projects where they actually belong, but this blog will stay static-first from now on.

The most important thing: **pick tools based on what you're building**, not because "React is trendy."
